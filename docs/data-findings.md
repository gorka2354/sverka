## Структура `id`

Формат `<домен>__<задача>::t<ход>`:

```
airline__10::t19
banking_knowledge__task_003::t7
retail__106::t3
telecom__mms_issueairplane_mode_on-bad_network_preference-...::t7
```

В telecom имя задачи кодирует набор поломок окружения (`airplane_mode_on`,
`bad_network_preference`, `break_apn_mms_setting`, суффикс `PERSONA_Hard`).

⚠️ **Строки одного диалога коррелируют.** Валидационный сплит делать **по `conv`**
(часть `id` до `::`), иначе ходы одного разговора попадут и в train, и в dev, и локальная
оценка будет завышенной.

## Фактический формат разметки транскрипта

**Совпадает с вкладкой Data и расходится с вкладкой Overview** (обе — `task-spec.md`).
Overview обещает маркеры `⟦ASSISTANT_TOOL_CALL name="X"⟧`, `⟦USER_TOOL_CALL name="X"⟧`,
`⟦TOOL_RESULT name="X" requestor="assistant"⟧`; вкладка Data описывает то, что реально в файле.
Верить Data.

Фактически в файле встречаются только:

| Маркер | Вхождений в 46 промптах |
|---|---|
| `⟦SYSTEM⟧` | 46 |
| `⟦USER⟧` | 267 |
| `⟦ASSISTANT · ход N⟧` | 449 |

В `response` — ровно один маркер `⟦ASSISTANT · ход N⟧` на пример.

Скобки — символы U+27E6 / U+27E7 (`⟦` / `⟧`). Строка `TOOL_CALL` встречается в тексте 87%
промптов и 50% ответов, но **не как отдельный маркер хода** — вызовы инструментов лежат
внутри тела хода. Схемы инструментов подаются в системном сообщении блоком `[AVAILABLE TOOLS]`.

проверить на реальном `test.csv` — там формат может отличаться от сэмпла.

### Фактическая разметка вызовов инструментов

Вызовы лежат **внутри тела хода**, строками с префиксами (`scripts/probe_data.py`):

```
⟦ASSISTANT · ход 2⟧
	→ TOOL_CALL get_user_details: {"user_id": "sofia_kim_7287"}
	← TOOL_RESPONSE get_user_details: {"user_id": "sofia_kim_7287", "name": {...}, ...}
```

Схемы инструментов подаются в системном блоке после заголовка `[AVAILABLE TOOLS]`:

```
- book_reservation — Book a reservation.
    user_id: string! — The ID of the user such as 'sara_doe_496'.
    cabin: string! [enum: business|economy|basic_economy] — The cabin class.
    flights: array! — An array of objects containing details about each flight.
        · flight_number: string! — Flight number, such as 'HAT001'.
```

Восклицательный знак после типа означает **обязательный** параметр, `[enum: a|b|c]` —
допустимые значения, `·` с увеличенным отступом — вложенное поле.

## Что размечено как галлюцинация (из `explanation`)

Выписки, задающие таксономию:

**Нарушение схемы инструмента.** «Агент передал объекты `payment_methods` с полями `id` и
`source`, тогда как схема этого тула в `[AVAILABLE TOOLS]` требует поля `payment_id` (string!)
и `amount` (integer!). Обязательное поле `amount` вообще отсутствует, а имена полей `id`/`source`
в схеме не предусмотрены — они выдуманы.»

**Действие в обход правила политики.** «Policy требует: „The API does not check that
cancellation rules are met, so the agent must make sure the rules apply before calling the API!"
… Агент вызывает `cancel_reservation` для KC18K6 и S61CZX, но ни одно условие не выполнено».
Проверка требует сопоставить даты создания броней и класс из истории с «текущим временем»
из политики.

**Неверный расчёт по правилам политики.** «В профиле membership: silver, бронирование —
cabin economy с одним пассажиром. По policy (silver + economy) полагается 2 бесплатных багажа,
то есть `nonfree_baggages` должно быть 0. Агент же передаёт `nonfree_baggages: 1`, что означает
платный багаж $50; при этом выбранная gift card имеет баланс всего $6.»

**Арифметика с неверной фильтрацией.** «Агент включает в сумму рейсы с датами раньше текущего
времени … даёт 402 + 306 + 308 + 16005 = 17021, тогда как предстоящими остаются только
402 и 306 с суммой 708.»

**Отсутствие обязательного подтверждения.** «Policy требует перечислить детали и получить явное
„да" перед любым изменением брони … агент не описал детали и не запросил подтверждения,
а сразу выполнил `update_reservation_baggages`.»

### Полный перечень категорий по ТЗ

Выписки выше — то, что встретилось в 23 объяснениях сэмпла. Организаторы на вкладке Data
перечисляют шире, и **эти категории надо держать в поле зрения, даже если в сэмпле их нет**:

> a fabricated fact/number/id, **a call to an unavailable tool**, wrong arguments,
> a violation of policy rules, **a false refusal**, etc.

- **Вызов недоступного инструмента** — проверяется механически: имя вызванного инструмента
  против списка из `[AVAILABLE TOOLS]`. Дешёвая и точная проверка. `[замер]` Срабатывает
  на 5 примерах, все положительные, ноль ложных.
- **Ложный отказ** — агент отвечает «не могу этого сделать», хотя по политике может. Чисто
  числовыми и схемными проверками не ловится вообще: нужен разбор политики и смысла отказа.

⚠️ **Исправление от 27.08.2026.** Ранее здесь стояло «в сэмпле он, похоже, не представлен».
Это неверно: **ложный отказ и преждевременная эскалация — второй по массовости класс,
5 из 23 положительных.** Ошибка возникла из-за того, что категория искалась по словам отказа
в тексте, а фактически она чаще выражена вызовом `transfer_to_human_agents` при неисчерпанных
доступных шагах. Полный перечень наблюдаемых категорий — в разделе ниже.

### Полная таксономия по всем 23 объяснениям — замер 27.08.2026

Разбор каждого объяснения, а не выборочные цитаты. Категории пересекаются: в одном ходе
может быть две ошибки, метка при этом одна.

| Категория | Штук | Ловится машинно? |
|---|---|---|
| Вызов инструмента, отсутствующего в `[AVAILABLE TOOLS]` (в telecom — диагностика на устройстве пользователя; в banking — discoverable-инструмент без предварительного `unlock`) | 5 | **да, precision 1.00** |
| **Ложный отказ / преждевременная эскалация** — `transfer_to_human_agents` или словесный отказ при неисчерпанных доступных шагах | 5 | нет |
| Нарушение правила политики при выполнении действия (условия отмены брони, истёкший контракт линии, возврат и обмен одного заказа, верификация по одному признаку вместо двух, порог утилизации кредита) | 5 | частично |
| Неверные аргументы вызова (нарушение схемы, выдуманные имена полей, невалидная модификация «старый id = новый id») | 4 | **да, нужен рекурсивный валидатор** |
| Выдуманный идентификатор или строка-заглушка в обязательном поле | 2 | **да** |
| Арифметика с неверной фильтрацией (в сумму «предстоящих» включены состоявшиеся рейсы) | 1 | частично |
| Заявление о действиях, которых в ходе нет (текст описывает вызовы, отсутствующие в ответе) | 1 | частично |
| Точный повтор ранее провалившегося вызова без изменений | 1 | **да** |
| Запрос данных, уже имеющихся в контексте (ложный запрос даты рождения) | 1 | нет |

Три категории из этого списка в прежней редакции документа отсутствовали: ложный отказ,
заявление о несовершённых действиях и повтор провалившегося вызова.

⚠️ **Отдельно: правило «один вызов за раз».** `[замер]` Строка «You should only make one tool
call at a time» есть в системном блоке **35 из 46** примеров: airline 12/12, retail 11/11,
telecom 12/12, **banking_knowledge 0/11**. В banking вместо неё действует только более слабое
«You cannot do both at the same time» (нельзя одновременно писать пользователю и вызывать
инструмент), которое многовызов не запрещает.

⚠️ **Но разметка за многовызов не наказывает, и это проверено.** Ни одно из 23 объяснений
не упоминает множественность вызовов. Multi-call — рядовое поведение: 53 хода ассистента
с ≥2 вызовами в истории промптов, это 23% всех ходов с вызовами, встречаются в 22 примерах
из 46, из них **9 с label = 0**, в том числе в доменах, где правило есть. Восемь строк, где
такой гейт срабатывает, размечены 1 по совершенно другим причинам.

**Вывод:** признак «≥2 вызова» коррелирует с меткой на этом сэмпле, но причинной связи не
имеет — это прокси сложности хода, а не нарушение. Права самостоятельной метки не получает.
Промежуточная запись «самый мощный из детерминированных сигналов» была ошибкой и отозвана.

### Что из этого следует

Задача ближе к **аудиту действий агента**, чем к проверке фактов. Значительная часть меток
машинно проверяема без модели: соответствие аргументов схеме инструмента, существование
вызванного инструмента, арифметика, сравнение дат с «текущим временем», наличие подтверждения
в предыдущих ходах. Это основание для детерминированного слоя каскада.

⚠️ **`explanation` запрещено использовать как вход** (прямая цитата ТЗ: «It is NOT an input»).
Оно годится только для двух вещей офлайн: построить рубрику судьи и размечать собственный
корпус. В `predict.py` его быть не должно — ни в каком виде.

Отдельно отметить: в одном объяснении встречается формулировка «**Новые ошибки этого хода**» —
то есть разметка относится к конкретному ходу, а не к диалогу целиком, и ошибка, допущенная
раньше и уже учтённая, повторно не засчитывается. Это важно и для парсера, и для промпта судьи.
